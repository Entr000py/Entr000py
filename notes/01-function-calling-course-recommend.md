# 用户说“别太跳”，课程库里却没有这个标签

> 场景为构造示例，用于讨论实现取舍，不代表已上线功能或实习成果。

用户下班后打开健身助手：“今天只有 20 分钟，想练核心。膝盖最近不舒服，别安排跳的。”

这句话不难理解。麻烦在于，课程后台可能只有训练部位、难度和时长，没有“包含跳跃”这个字段。模型能把要求提取出来，检索服务却没有足够的数据执行。

## 三门候选课，哪门能展示

假设按“核心、初级、20 分钟以内”筛出了这些课程：

| 课程 | 后台已有标签 | 核对动作清单后发现 |
|---|---|---|
| 18 分钟核心循环 | 核心、初级 | 包含开合跳 |
| 15 分钟垫上核心 | 核心、初级 | 没有跳跃，但没有伤病适用性审核信息 |
| 12 分钟腹部训练 | 核心、初级 | 动作资料不完整 |

如果排序只看目标和难度，第一门可能排在最前。把“膝盖不舒服”提取成“避开膝盖”也解决不了：训练部位描述的是练哪里，不能直接表示动作会给哪个关节带来负荷。

这一步需要回到课程资料。是否包含跳跃，可以根据完整动作清单审核；涉及伤病的适用性，则需要专业判断。模型不能根据“垫上”“初级”这样的标题和标签，推断一门课适合膝部不适者。

第二门满足“不跳”的条件，也不能因此被介绍成“适合你的膝盖”。第三门的信息不足，不能默认符合要求。

## 工具参数要和真实字段接得上

对这个例子，模型可以向工具提交：

```json
{
  "goal": "核心",
  "max_minutes": 20,
  "exclude_jumping": true,
  "reported_discomfort": "膝盖最近不舒服"
}
```

服务端检查参数类型、目标枚举和时长范围，再执行筛选。`reported_discomfort` 保留用户原话，进入后续风险处理；它不直接转换成诊断，也不作为“这门课安全”的依据。

只有课程库有经过核对的动作信息，`exclude_jumping` 才是可执行的条件。如果暂时补不齐全部课程，可以先在资料完整的课程子集中提供这个筛选，并明确覆盖范围。接口接受一个字段，却在查询时忽略它，会比直接说明不支持更容易误导用户。

对于当前身体不适，助手还应说明无法判断训练适宜性，不能直接给出适合其伤情的推荐；必要时建议暂停训练并咨询专业人员。

## 不够四张卡片，怎么办

假设页面原来固定展示四门课，严格筛选后只剩一门。产品上最容易出现的妥协是自动放宽时长或动作要求，把卡片补满。

但“只有 20 分钟”和“别安排跳的”都不是排序偏好。候选不足时，应少展示或明确无结果；需要改变条件，就让用户确认。不能在接口里悄悄放宽，再让生成模型编一句“为你精选”。

用户点“不感兴趣”也要进入后续检索。没有更详细的反馈时，可以在约定有效期内抑制这门课；不能从一次点击推断用户永远不喜欢某位教练或全部核心课程。

## 上线前先查这些结果

用固定课程样本检查：含跳跃的课有没有漏进来、资料缺失的课有没有被当成符合条件、无结果时有没有偷偷放宽要求，以及刚拒绝的课程是否马上再次出现。

这些检查过关后，再比较推荐后的开练情况。分母要明确是看到了推荐的用户还是全部发起请求的用户，无结果请求不能悄悄从统计中消失。身体限制是否被遵守，需要单独核对，不能用开练率证明。

这里没有对应的实验记录，因此不报告提升比例。Function Calling 在这个流程里解决的是条件传递；推荐是否可靠，还取决于课程数据能不能支持这些条件。
